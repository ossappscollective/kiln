# ADR 0068: Tint the interface with the app icon's colours

Status: web and server implemented, unit and server tested (contrast is tested as a property over every hue, several chroma levels and both themes). **Not viewed in a browser**: the look of tinted surfaces in both themes and the extraction on real store icons are unverified. No migration.
API: [api/apps](../api/apps.md) (`GET /apps/appearance`, `PUT /apps/{id}/appearance`). Design: [design-system](../design-system.md) "App tint". Builds on [ADR 0049](0049-testflight-feedback.md) (same-origin images, CSP `img-src 'self' data:`).

## Context

Every app page used the one product accent, so a person with ten apps could not tell at a glance which one they were in, and the reviews inbox mixed all apps in one colour. The app icon already carries the app's identity.

## Decision

**Extraction (client, deterministic).** The icon is loaded from this server only (the icon route, `iconSrc` refuses anything else), drawn on a 32 by 32 canvas, and `lib/tint/palette.ts` quantises the pixels in OKLab (15 degree hue bins by three lightness bins), drops near transparent, near white, near black and nearly grey pixels, weights by chroma times population, merges hues within 20 degrees and returns up to three colours; an icon with no usable chroma is `neutral` and gets no tint. The result is cached in `localStorage` per app and icon URL (`kiln.tint.v1.<appId>`), so the tint is applied from the cache before the first paint and the icon is decoded again only when its URL changes. No palette (not loaded, failed, neutral) means no tint: a colour invented from the app id would be wrong. No image decoder exists on the server and none was added.

**Derivation.** `lib/tint/tokens.ts` keeps the hue of the primary colour, caps the chroma at 0.17 and searches the OKLCH lightness (closest to the icon's own) until every pair meets WCAG 2.x against the real theme surfaces (`lib/tokens.ts`, tested against `theme.css`): accent for borders and indicators 3:1; accent ink for text and icons 4.5:1 on every surface and on both tints; hover 4.5:1; solid with its text 4.5:1; body, secondary and faint text keep 4.5:1 on the subtle and strong tints and under the glow (the tint opacity is lowered until they do). Chroma is clamped to sRGB. When a pair cannot be met the result is null for that theme and the whole app keeps the default accent (one theme tinted and one not would look broken). `prefers-contrast: more` and `forced-colors` re-map nothing.

**Scope.** One wrapper attribute, `data-app-tint`, carries the inline style (`--tint-l-*`, `--tint-d-*`); `styles/tint.css` picks the set of the current theme (data-theme, else prefers-color-scheme: the mechanism of `theme.css`) and re-maps the accent tokens only inside that subtree. It sits on the app page container (`AppShell`), the app card and the "This app" group of the sidebar (`AppNav`), and, for the page glow only, `data-app-tint-glow` on the shell column re-maps just `--ambient`. Not tinted: top bar, breadcrumbs, search, account menu, notifications, the workspace group, the portfolio and all-apps pages, workspace settings, toasts (outside the app subtree), and the status colours, focus ring, surfaces, ink and borders (never re-mapped; a test asserts it). Dialogs (`showModal` draws in the top layer but inherits from the DOM parent) and anything with `data-tint-reset` get the default tokens back through `--*-default` snapshots on `:root`. **Decision: the pending cart drawer (a native dialog) stays neutral**, like every dialog and drawer: it is a workspace action surface that lists changes of several apps' records. A test asserts that every selector of `tint.css` is under `[data-app-tint`, that every re-mapped token is restored for dialogs, and that no colour is written there.

**Opt-out.** A personal switch (account menu, default on, `localStorage` `kiln.tint`, like the theme; there is no server-stored per-user preference for appearance) turns every tint off for that person, in app pages and the inbox. Per app, in app Settings, section Appearance: Auto (icon colours), Off for this app, Custom colour (any colour is safe: the same derivation applies; a grey or unreadable pick gives no tint and the section says so; a live preview and the derived tokens with their measured contrast are shown). Stored per record of the app in `workspace_settings` under `app.<appId>.appearance` (no migration; `auto` is no row; deleted with the app; audited as `app.appearance_update`); read in one request for the workspace; changing it needs `apps.write`. Updates apply at once (a reactive store), with no reload; tint is only inline custom properties and shadows, so nothing shifts.

**Reviews inbox.** The one place the tint is used outside an app route: each row wears its app's tint (start edge, icon ring, app name in the accent ink; the review itself and its buttons keep the default accent). With the personal switch off rows are neutral with the app icon chip only. The inbox also gets a real app filter (see ux-ia).

## Consequences

- A tinted token pair can never fall under WCAG on a theme surface, by construction and by test; the cost is that some saturated mid-lightness colours (yellow, lime, deep blue) are darkened or lightened more than a designer might like, or fall back.
- The extraction runs in the browser on every device once per icon version; a failure is silent and costs only the tint.
- Gaps: the tint of the second record of an app that has a different icon follows the record in the address; iOS and Android records are saved together, so a record added later reads `auto` until saved again.
