# ADR 0063: Store assets changed in the repository, proposed while a release is prepared

Status: server, core and web implemented, tested against fakes (a fake repository with three commits, a fake store); **not viewed in a browser**. No migration.
API: [api/release-asset-proposal](../api/release-asset-proposal.md). Builds on [ADR 0054](0054-pending-cart.md) (the cart), [ADR 0059](0059-listing-fixes-via-cart.md) (staged texts, the lock) and the Graphics staging of [ADR 0012](0012-assets-two-way-sync.md).

## Context

A person who prepares a release often changed the store texts or screenshots in the repository (fastlane metadata, the layouts Kiln already reads) and then has to remember to stage them one by one on the Store listing and Graphics pages. The repository comparison (`compareRepo`, `compareMedia`) is off by default and is about warnings, not about a release.

## Decision

1. **A proposal, never an action.** The Assets step of Prepare release shows a card "Store assets changed in the repository" (`AssetProposalCard`). Staging happens only on the click of "Stage selected", through the existing staging code (`stageText`, `stageAssets`: same gates, limits, metadata lock and audit). Nothing is pushed to a store.
2. **What is "new since the last release".** The repository is read at two commits: the **base** (the source of the previous release: the commit of its build in `build_links`; else the newest repository read this tool made, `listing_snapshots.source_ref`, at or before that release's last store update) and the **target** (the commit of this release's build; the build number is the query's `build`, else the stored release of that version; else the default branch tip, resolved). Without a base (`noPreviousRelease`, also when the base commit cannot be read) every repository value that differs from the store is a candidate and the card says so. Texts: per locale and field of the app's listing target (the same folders as every other read); graphics: per set (locale, kind, device) of the asset index of the commit, by the list of paths and git object ids. An item is listed only when it changed between base and target **and** differs from the store (the editable version's texts where the store has a draft, else the live ones; graphics by the existing store comparison at the target commit) **and** is not in the cart. Counts of what was left out are returned (`skipped`).
3. **Checks first.** Before anything is offered, the server runs the checks that exist on the repository side: the listing checks (`checkListing`, with the page as it would be after the proposed texts) and the listing limits (`sideProblems`), and the graphics rules the asset index already computes for the target commit (sizes, counts, limits). They are returned as `issues` (errors, warnings, tips; each tied to an item), errors first, and an item with an error is `hasErrors`. The card shows the findings before the items; items without errors are checked, items with errors are unchecked, marked "Has issues", and staging them needs a confirmation (`acceptIssues`, else `409 has_issues`).
4. **No setting needed, but only with a repository.** Reading the repository here is part of preparing a release and does not require `compareRepo` / `compareMedia`; those stay about the warnings of the listing and Graphics pages. An app with no linked repository is never read (`unavailable: no_repository`); an app whose repository holds no store listing for it shows nothing (`no_repo_metadata`).
5. **Locks and platforms.** The Apple lock (`metadataLock`: no editable version) still applies: the changes are listed, the card says staging is not possible until a new version is prepared, and the stage route answers `409 metadata_locked`. Google Play never locks. The App Store name and subtitle (app information, not stageable) are counted in `skipped.notStageable`, never offered.
6. **The server is the author.** A request names item ids; the proposal is computed again and the matching items are staged. A client sends no text and no path. An item already in the cart is not written again (`already_staged`), and a cart item a person edited is kept (`kept_edited`) and shown as "already staged". Staging twice therefore never duplicates. Texts are staged as `local` text with the repository's value (like the fixes of ADR 0059); graphics as the repository's set pinned to the target commit.
7. **The decision is remembered per release.** `skip`, `later` or `reopen` is saved in `workspace_settings` under `app.<appId>.assetProposal.<version>|<track>` (no migration; deleted with the app) and audited (`release.asset_proposal_decided`). Skipped: a one-line note with "Show again". Later: collapsed with a "Review" button. The card is never shown again by itself.
8. **Untrusted content and limits.** Repository text has control characters removed and is held to the staging limit (longer texts are not offered); graphics are read by the asset index with its file, byte and transfer budgets, and thumbnails go through the file route with its size and type guards. At most 400 items are listed (a note says so). Item ids are only looked up in the computed proposal. `version`, `track` and `build` must be plain labels (letters, digits, `.`, `_`, `+`, `-`, space; at most 40). Audit entries hold item ids and commits, never a text. The index read is rate limited like the Assets tab (cache hits are free).

## Consequences

- "Which commit changed it" per item is not shown: the connector has no history call, so the card names the two commits it compared. A cheap per-file history would need a new connector method.
- The previous release's source depends on `build_links` (CI runs linked to builds). Where no link exists the fallback is the repository read nearest to the previous release's last update; where that is missing too the card says "no previous release found".
- Google Play: the build is not chosen from the step (version codes), so the target is the default branch tip unless a stored release of the version has a linked build.
- The proposal is not on the Timeline. The Releases list shows a count only, from a cached summary endpoint ([ADR 0064](0064-pending-count-and-asset-hint.md)); the full proposal is still computed only in the Assets step.

## Not verified (UNVERIFIED)

Not viewed in a browser (layout, dark mode, keyboard use of the checkboxes and the dialog). Never run against a real repository, store or Postgres (the Postgres variants of the tests skip without `KILN_TEST_POSTGRES_URL`). The previous-release lookup was tested with linked builds and without any release; the repository-snapshot fallback has no test of its own.
